# Harness Consumer API lifecycle v0

Status: canonical distribution contract and architecture decision.

## Decision and scope

Latest source supports both Consumer APIs: v0 is the legacy compatibility
**distribution**, v1 the canonical-only distribution. `src/harness/**` owns
semantic/runtime implementation; root/dotted facades are external compatibility
surfaces. Physical runtime migration is complete. API retirement and
installed-package/source-tree execution are independent decisions.

The distribution-owned machine contract is
`spec/distribution/consumer-api-lifecycle-v0.yaml`. Repository-layout remains the
only owner of physical facade mappings and canonical targets; lifecycle records
refer to registry identities, without duplicating those mappings. This decision
introduces no Core entity, domain lifecycle or workflow engine.

## Lifecycle

`SUPPORTED → DEPRECATED → EOL → REMOVED`. Each adjacent transition requires an
explicit distribution decision recorded in the API's decision reference; no
calendar schedule or implicit layout-based transition exists. Current v0 is **DEPRECATED** and v1 is **SUPPORTED**, authorized by
[ADR-CONSUMER-API-V0-DEPRECATION](harness-consumer-api-v0-deprecation.md).
No EOL or removal transition is authorized.

| State | Operational obligation |
| --- | --- |
| SUPPORTED | Latest source accepts the API, materializes its Pack, supports wrappers/tooling and runs required compatibility tests. |
| DEPRECATED | Latest source still works; new consumers must use v1; migrate existing consumers to v1; compatibility defects remain supported until EOL. |
| EOL | Latest source has no obligation to accept/materialize/support that API. Immutable historical Harness revisions remain historical artifacts and can still contain working legacy Packs. |
| REMOVED | After explicit prior EOL and a separate removal decision, v0-only source may be physically deleted and related registries/validators simplified. |

EOL makes the rows below deletion candidates, not deletion instructions. Removal
must update active first-party callers, compatibility tests, distribution
manifests and registries together. Historical documentation/evidence remains
historical and must not be rewritten to pretend older revisions ceased to exist.

facades and two dotted `adapters/*` facades. All exist in source for the still
materializable v0 distribution; v1 needs none. All 49 have active first-party
registry-driven structural/Pack checks; direct per-identity references vary. They are `DELETE_AFTER_V0_EOL`, subject to explicit
EOL/removal decisions and first-party reference updates.

automatically deleted solely by retiring its two facade modules.

## Repository-wide reference evidence

`spec/distribution/consumer-api-usage-v0.json` is a reproducible path-level
snapshot generated by `usage_inventory` in the focused lifecycle validator.
It records each physical/logical surface, derived canonical target and users in
five categories: canonical runtime, distribution/tooling (including distribution
and architecture mapping contracts), validators/tests,
active documentation/examples, historical documentation/evidence.

Canonical runtime dependency scanning uses absolute Python AST imports, including
`from adapters import canonical_graph`; canonical submodule imports are not
mistaken for the Core alias `harness`. Outside runtime, bounded legacy paths and
dotted identities also discover command examples, test probe strings and mapping
references. Reference hits are evidence requiring interpretation, not proof of
production dependencies. Dynamic/runtime fallback is exercised separately by
the stripped-source ratchet. The scanner excludes its own contract, generated
snapshot, design report and scanner implementation to avoid self-references.

Findings: no canonical runtime imports of legacy identities. First-party
validators/tests deliberately use legacy entrypoints and therefore must be
adapted at removal; those are compatibility evidence, not production runtime
dependencies. `distribution/harnessw.py` deliberately invokes root
`consumer_pack.py` for v0 and canonical module execution for v1. Active docs,
examples, bootstrap and workflows also retain references; current support makes
them legitimate, but EOL/removal work must review them. Historical hits below
are references only and never retirement blockers. **No registered facade is
historical-only**, because every facade is still distributed in v0 and covered by registry-driven checks.
Individual paths under `docs/audit/`, `docs/legacy/`, `docs/plans/` and frozen
`spec/assurance/evidence/` are classified historical; the JSON enumerates them.

The machine snapshot lists reference-bearing file paths, not invocation counts.
All canonical runtime imports of legacy identities remain zero. Shared
registry-driven compatibility validators are enumerated separately. Active
incidental CI/README/skill executions now use canonical identities; v0 wrapper
and intentional compatibility probes remain visible. Physical presence alone
is not public API membership. The contract's owned onboarding surfaces must
recommend v1; legacy-specific documents remain compatibility references.

## Independence and evidence

Reuse TD-DIST-001/002 for HA-A18 (A18-F03/F05/F06), TL0/TL1 contract
mutations and TL2 source/materialization/CLI composition, O1 contract oracles.
CI registration follows HA-A19 and the existing check registry/full gate.

`validate_consumer_pack.py` derives the stripped facade set mechanically from
repository-layout, copies the current candidate into an isolated temporary source,
unlinks every registered CLI/module facade and removes the upper `adapters/`
tree. It preserves both package initializers. A fresh virtual interpreter contains only copied PyYAML, with no Harness
installation or global site packages; an outside-source probe proves Harness is
not importable. With PYTHONPATH removed and user site disabled, an import hook
rejects legacy identities; every canonical imported module must resolve inside this copy's
`src/harness`. It materializes v1 from that source, checks `consumer_api: v1`,
then runs the existing canonical CLI/import and six representative Scenario Suite
acceptance cases against both stripped source and resulting Pack. A mutation
introducing `import consumer_pack` in canonical runtime must fail. No Harness
installation or `PYTHONPATH=src` is needed.

Existing v0 Pack/wrapper acceptance remains required and unchanged. Existing v1
acceptance proves zero production root facades, absent upper adapters, retained
scenario tooling, clean-target wrapper and canonical module execution. Pack
integrity rejects tracked hash mismatch and arbitrary untracked files while
ignoring only `.pyc` inside `__pycache__`.

The focused lifecycle validator checks exact registry coverage, mechanical dotted
mapping, known/existing identities, supported-state facade presence, immutable
classification boundaries and protected exceptions. Usage drift fails validation;
regenerate the JSON using `usage_inventory` and review semantic classifications
when references change. The current-source state ratchet requires v0 DEPRECATED and v1 SUPPORTED,
with an explicit deprecation decision, canonical v1 onboarding and unchanged
compatibility obligations. Inventory separates `physically_present_in` from
`public_consumer_apis`; v1 Core access is `harness.project_model.core`.

## Consequences and follow-up decisions

No compatibility file or registry mapping is deleted. No Core semantics,
provider behavior, Scenario DSL, package installation or execution model changes.
Retirement inventory creates a bounded removal checklist without conflating
compatibility evidence with canonical dependencies. Execution bridge removal,
Core re-export retirement and actual provider tooling relocation require their
own architecture decisions. V0 deprecation is explicit distribution policy; EOL/removal remains future
explicit distribution work, with no dates implied by this tranche.
