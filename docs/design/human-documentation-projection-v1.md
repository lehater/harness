# Human Documentation Projection v1

Status: canonical v1.

## Goal

Generate useful human-readable project documentation from accepted engineering
knowledge without creating a second source of truth, widening the selected
Consumer scope implicitly, or treating generated prose as canonical knowledge.

Human Documentation Projection is a view above Engineering Graph/Core. It does
not add a Documentation Authority, Capability, Core entity, workflow state or
approval concept.

## Canonical boundary

Canonical engineering truth remains in project CanonicalArtifacts.

Generated human documentation:
- is disposable;
- provides no CapabilityIds;
- may be regenerated or deleted without changing target state;
- must remain source-bounded;
- must expose unresolved Questions/gaps instead of silently completing them.

Existing project-native artifacts remain canonical in their native form.
Harness does not require migration into a universal documentation schema.

## Projection pipeline

```
Engineering Graph + Core/project realization + Consumer
        ↓
deterministic projection manifest
        ↓
project-owned presentation recipe
        ↓
source-bounded projection plan
        ↓
validated narrative projection IR
        ↓
human-readable REVIEW or HANDOFF package
```

Visual assets already generated by project-owned deterministic renderers may be
included when their declared canonical sources are inside the selected manifest.

## Projection manifest

`compile_manifest` derives the documentation source boundary.

Inputs:
- Engineering Graph;
- exactly one project integration form: an accepted Core realization, or an authoritative source graph plus Harness projection;
- selected Consumer;
- optional explicit extra CapabilityIds;
- optional Harness/project baseline identities;
- optional source root for file digests.

The manifest contains:
- selected Consumer;
- Consumer capability closure;
- explicit extra capabilities;
- target state;
- providers by capability;
- direct provider artifacts;
- canonical dependency closure;
- Authority ownership;
- canonical source paths and optional SHA-256;
- unresolved required capabilities;
- relevant unresolved Questions;
- deterministic manifest digest.

For source-graph integrations, Harness validates project/capability alignment
for the selected Consumer before compiling the manifest.

The compiler does not infer domain, architecture or product semantics from
arbitrary prose.

### Scope widening

The selected Consumer is the default scope.

A caller may explicitly add extra CapabilityIds for a documentation purpose.
Unknown capabilities fail closed.

Implicit repository-wide widening is forbidden.

## Presentation recipe

A project may declare a small `harness-human-projection` recipe.

The recipe owns presentation/navigation policy only:
- document grouping;
- section grouping;
- titles/purpose;
- source selection.

A section may select accepted sources by:
- CanonicalArtifact id;
- CapabilityId;
- Authority.

Every selected source must already be inside the compiled manifest. A recipe
cannot use itself to widen semantic scope.

The recipe must not contain product/domain/architecture assertions merely to
make the generated document complete.

## Narrative projection IR

Narrative prose is represented first as
`harness-human-projection-ir`.

Every planned section must exist.

Every substantive claim must:
- contain human-readable text;
- cite one or more CanonicalArtifact IDs;
- cite only artifacts allowed for that section.

When evidence validation is enabled, every cited source also requires an excerpt
present in the current canonical source. Optional locators may identify the
source location.

This provides machine-checkable source bounding and freshness. It does not
prove that a paraphrase is semantically perfect; semantic review remains
required.

## Source freshness

When the manifest was compiled with a source root, source SHA-256 values may be
recorded.

`validate_manifest_sources` fails when a canonical source changed after
manifest compilation.

Narrative IR is also bound to the current manifest digest.

Therefore changing accepted source knowledge invalidates stale projection
packages instead of allowing them to masquerade as current documentation.

## Package modes

### REVIEW

Contains:
- README;
- manifest;
- projection plan;
- projection IR;
- generated human documents;
- optional eligible visual assets.

Canonical sources are referenced but not copied.

### HANDOFF

Contains the REVIEW package plus snapshots of every canonical source selected by
the manifest.

HANDOFF is for offline/review transfer only. The copied source snapshot is not a
new canonical store.

## Visual assets

`resolve_visual_assets` accepts project-owned visual-projection declarations.

An asset is eligible only when every declared canonical source is already in the
human-projection manifest.

Outputs:
- must be repository-relative;
- may be digest-bound;
- are copied into the package;
- remain generated views rather than CanonicalArtifacts.

Human Projection does not define how Structurizr, PlantUML or other project
visuals are generated.

## Non-goals

v1 does not define:
- a fixed software-document taxonomy;
- one mandatory Markdown template;
- a Documentation Authority;
- a universal canonical document schema;
- automatic semantic repair;
- repository-wide prose inference;
- an LLM-specific prompt protocol;
- canonical status for generated prose;
- a generic typed/source-native renderer framework.

Existing typed Harness workspace renderers and project-native deterministic
renderers remain separate mechanisms. They may feed future projection backends
when justified by real consumers.

## Agent procedure

Use `skills/agent/human-documentation-projection/SKILL.md` only after manifest
and recipe compilation.

For each section the agent reads only the allowed canonical source set, produces
projection IR, validates it, and only then renders the human document.

Generated documentation being replaced or benchmarked is not a semantic source.

## Acceptance evidence

Harness acceptance proves:
- deterministic Consumer closure;
- explicit capability widening only;
- recipe source-boundary enforcement;
- projection-IR section/source enforcement;
- source digest freshness;
- required evidence excerpts;
- REVIEW package materialization;
- HANDOFF source snapshotting;
- eligible visual-asset inclusion;
- stale visual detection;
- incomplete target/gap representation.

Cross-project validation was performed on current main revisions of:
- NAPMS BACKEND-IMPLEMENTATION;
- NAPMS FRONTEND-IMPLEMENTATION;
- Nutrition Management IMPLEMENTATION;
- Nutrition Management FRONTEND-IMPLEMENTATION.

The two projects use different canonical graph shapes and different frontend
design structures. The same compiler required no project-specific semantic
logic.

## Policy

- canonical truth stays in CanonicalArtifacts;
- Consumer closure defines the default documentation boundary;
- explicit extra capabilities are visible scope widening;
- recipes control presentation, not engineering truth;
- every narrative claim is source-bounded;
- generated documentation never provides capabilities;
- unresolved knowledge remains visible;
- semantic auto-fix is forbidden;
- generated packages are disposable projections.

No Core change is required.
